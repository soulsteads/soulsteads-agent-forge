---
name: forge-operations
description: Register permitted work, schedule it with an explicit time zone, inspect durable Forge run evidence, and investigate failures through Forge MCP tools or the operational CLI.
---
Use an authenticated Forge MCP server or the operational `soulsteads-forge` CLI configured by the operator. Never open Forge databases or invoke a second executor.
1. Call `forge_snapshot`; inspect available types, scoped work/run summaries, schedules and failures. Read complete definitions with `forge_work {work_id}` or `soulsteads-forge work show ID`.
2. Register an immutable definition with `forge_register`. Core types are `echo` (`text`, optional `delay`), `fail` (empty input), and `model` (`model` alias, `prompt`, optional `expect` substring). Model aliases are operator configured. No plugin is required.
3. Call `forge_run` with a unique key for a new requested operation. Reuse the same key if the response is lost. A new key means a new operation, not a safe replay.
4. Inspect the returned run ID with `forge_inspect` until terminal. Large nested values are explicit previews; select `effect_id` or `step_id` (CLI `runs inspect ID --effect-id EFFECT` / `--step-id NUMBER`) to read one exact record. Record the run ID, actual output, step timings and verification outcome, not merely successful admission.
5. For a new recurring schedule, preview the cron and explicit IANA time zone with `forge_schedule_preview {cron,tz}`, then create it with `forge_schedule {name,work_id,cron,tz}`. Preview stores nothing. Five fields start with minute and are normalized with leading second zero. Six fields start with second. Use the returned canonical schedule name in later calls. Missed ticks are never backfilled.
   - **Edit in place.** Read `forge_schedule_show {name}` before editing. Use `forge_schedule_update` with the same `name` and the fields to change: `cron`, `tz`, `params`, `enabled`, or `tags`. Preview the resulting cron and time zone before a timing change. Omitted fields stay unchanged. Use `params: null` to clear parameters and `tags: []` to clear tags. The schedule name, associated work, and occurrence history are retained. A change to timing or parameters keeps the previous revision. Changing the associated work requires a new schedule name.
   - **Confirm the edit.** Read `forge_schedule_show {name}` after the edit, including after an error or timeout. Check the requested fields and `pending_edit` before treating the revision as applied. If `pending_edit` is null and the readback matches, no further edit is needed. While an edit is pending, top-level timing and parameters reflect the native schedule when it exists. If `pending_edit.native_present` is true and you are authorized to finish that recorded edit, resubmit only the same name and the exact saved values: `pending_edit.schedule` as `cron`, `pending_edit.cron_timezone` as `tz`, and `pending_edit.params` as `params` (send null explicitly when recorded). Leave out `enabled` and `tags`. The current pause state is preserved. If the schedule is active and you need to stop future ticks, use `forge_schedule_action {name,action:"pause"}` when authorized and `actions.pause` is true. Pause leaves the edit pending. Recheck the same name afterward. If the native schedule is missing or the outcome remains unclear, stop and ask the operator to reconcile it. Do not create a replacement or trigger a run to resolve an unconfirmed edit.
   - **Read due outcomes.** `forge_schedule_occurrences {name}` lists recent due occurrences newest first, with stable `occurrence_id`, `scheduled_time`, `handoff`, and the admitted `run_id` and its status and output when available. A failed handoff can still have admitted a run. Read the full result with `forge_inspect`. The occurrence's `outcome` is derived from the run, including `succeeded`, `failed`, `cancelled`, `running`, `not_admitted`, or `handoff_pending`. `forge_schedule_show {name}` also shows native status, last fired time, upcoming ticks and outcome counts. Pause or delete a settled test schedule when finished.
   - **Run once only when explicitly requested.** `forge_schedule_trigger {name}` (CLI `schedules run NAME`) starts a new manual run using a settled schedule's saved work and parameters. A paused schedule stays paused. Each call starts a new run, so never repeat it to retry. If the call errors or times out, read `forge_schedule_show` for a `kind: manual` occurrence first.
6. If a run stays `ENQUEUED`, call `forge_queues {queue:"work"}` (CLI `soulsteads-forge queues show work`) before you act. It shows the stored native limits, home-local counts, what holds each slot (for example `durable_sleep` until a time) and each of your waiting runs' `wait.reason` (`queue_capacity`, `native_delay`, `rate_limited` or `not_determined`). It never reports a queue position or start estimate. An empty or short list is proof of absence only if `members_listing.complete` (or that state's `by_state` entry) is true; likewise for recent results with `recent_window.complete`. Otherwise use `forge_runs` with a status filter. A `null` `capacity.saturated` or `capacity.free` means unknown, not free. Do not create extra runs to "push" the queue. Cancel only a waiting run you no longer need: one cancelled before dequeue never starts. Other actors' work appears only as counts.
7. Diagnose failures by inspecting steps, logs, definition, output and effect receipt. `forge_retry` only permits definite failures with no completed/unknown external effect. Never evade this by using a new manual run key.
8. `forge_cancel` is cooperative and cannot undo active external calls. `RECOVERY_REQUIRED` means the external outcome is unknown. Stop and ask an authorized operator to reconcile provider evidence after the operation settles. Do not infer no effect from timeout, cancellation, or process death.
The Rust binary embeds this skill: `soulsteads-forge skill` prints it for installation into an explicitly chosen native skill directory.
Home and other Soulsteads products are optional. Credentials stay in environment variables/private operator configuration, never in prompts or evidence.

## Shell agents using the CLI

Use the same workflow above through these commands when shell access is available. The operator supplies `FORGE_TOKEN` privately; `--token-env NAME` can select another environment variable and `--url URL` selects the service (default `http://127.0.0.1:8110`). Never read, print or place credentials in command arguments. Operational commands use only the HTTP service, never local state. Results are JSON on stdout; errors are nonzero with sanitized stderr.

- Discover: `soulsteads-forge snapshot`; `soulsteads-forge plugins list` includes extension input schemas.
- Define: write one JSON definition with only `type` and `input`, then `soulsteads-forge work register ID --definition FILE`; `--definition -` reads stdin. Definitions are immutable; do not overwrite changed intent.
- Execute: `soulsteads-forge work run ID --key KEY`; inspect the actual returned ID with `soulsteads-forge runs inspect RUN_ID` until terminal. Reuse that key after a lost response.
- Schedule: preview with `soulsteads-forge schedules check --cron '0 9 * * *' --tz America/Chicago --json`, then create a new schedule with `soulsteads-forge schedules create NAME --work-id ID --cron '0 9 * * *' --tz America/Chicago`. Use the returned canonical name for `schedules show NAME --json`, `schedules pause NAME`, `schedules resume NAME`, and `schedules delete NAME`. Read due outcomes with `soulsteads-forge schedules occurrences NAME [--limit N]`, then `runs inspect RUN_ID`. `schedules status` and `schedules history NAME` give human-readable summaries (`--json` for canonical results).
- Edit a schedule: `soulsteads-forge schedules edit NAME --cron '0 10 * * *' --tz America/Chicago`. Omit timing flags you want to keep. Use `--params FILE` (or `--params -` for stdin) or `--clear-params`, `--enable` or `--disable`, and repeatable `--tag TAG` to replace the tag set or `--clear-tags` to clear it. Read `soulsteads-forge schedules show NAME --json` afterward, including after an error or timeout. For authorized resubmission of a pending edit with a native schedule, supply only `--cron` and `--tz` from `pending_edit.schedule` and `pending_edit.cron_timezone`, and `--params FILE` with its exact parameters or `--clear-params` for null. Leave out enable, disable, and tag flags. Follow the same pause and readback rules above.
- Queue capacity and wait reasons: `soulsteads-forge queues status` or `queues show work` (`--json` for the canonical result).
- Diagnose/control: `work list`, `work enable ID`, `work disable ID`, `runs list`, `runs cancel RUN_ID`, and `runs retry RUN_ID --key KEY` follow the same authority and effect rules as MCP.
- Workflows/runs for people: `workflows validate|create|show|run` and `runs search|show` print readable text; add `--json` for the canonical result. `workflows run ID --param K=V --wait` prints the key it used and exits nonzero unless `SUCCESS`. `runs show RUN_ID --json` includes `workflow.steps[].state/output/reason` and `workflow.failure`. MCP equivalents: `forge_validate {definition}` (checks without storing, located diagnostics) and `forge_runs {work_id?,status?,limit?,before?}` (scoped search, `next_before` cursor).
- Only an authorized operator with settled provider evidence should use `runs reconcile RUN_ID --decision completed|not-applied --note TEXT --settled [--output FILE]`. Do not infer `not-applied` from failure, timeout, or cancellation.

Input and request limits are 1 MiB; response limit is 4 MiB. Inspect a specific run if a snapshot is too large. List history is the latest 100 scoped runs. Do not treat admission, schedule creation, or a successful CLI exit as proof of completed work: inspect actual terminal output and due execution.

## First-class workflows and agents

Discover `snapshot.types.workflow` and `.agent` before authoring. Register the same outer `{type,input}` definition via CLI/MCP/dashboard.

- Workflow input has ordered `steps` with unique `id`, earlier `needs`, and `action:{type,input}` or `action:{work_id,params}`. Use typed `{"$ref":"/params/task"}` / `{"$ref":"/steps/ID/output/text"}` or textual `${/params/task}`. Only declared earlier dependencies are visible. Optional `params` supplies defaults; optional `output` maps retained outputs. Named agent/workflow references use fresh parameter contexts; pass parent data through explicit `params`.
- Agent input has configured `model`, `prompt`, optional `instructions`, and explicit `tools:[{name,type:"plugin.NAME"}]`. Set bounded `max_rounds` and `max_tool_calls` when appropriate (max/default 8 and 32); optional `output_schema` validates final JSON. The actual model chooses allowed tool names/arguments; retained tool-call IDs and results feed the next round. Do not label a single plain completion as tool-loop evidence.
- Manual `work run ID --key KEY --params FILE` and `schedules create ... --params FILE` accept a JSON object (`-` for stdin). MCP/API `run` and `schedule` accept optional `params`. Values override defaults; changed params with the same request key are refused. Root ordinary leaf work refuses nonempty invocation params.
- Inspect workflow output `.steps` and `.output`, agent output `.text`, `.json`, `.tool_calls`, `.messages`, native step timeline, and the per-call `effects` list. Verify actual model-selected calls and final output. Unknown effects require settled provider evidence with the exact `effect_id`; CLI `runs reconcile ... --effect-id ID`, MCP/API `reconcile.effect_id`.
- Pending process-loss recovery reuses native checkpoints and verified receipts. Cancellation fences future calls. Reconciliation retains evidence without resuming the failed workflow. This MVP refuses flow retries after any external effect history; never evade that fence with a new request key or copied definition.
- Bounds: 32 steps per workflow, nested depth 4, total authored nodes plus model turns and calls 64, context 1 MiB, strings 64 KiB. References are data-only; no eval, raw shell actions, legacy gates/foreach, implicit endpoints or tool grants. Existing actors need explicit workflow/agent/model/plugin type permissions.

## Harness-backed agent workloads

`snapshot.types.harness` and `soulsteads-forge runners list` (MCP `forge_runners`) show the operator-approved runner profiles, observed harness versions/availability and the adapter capability matrix. A `harness` workload (standalone work, or a workflow step with typed `inputs` and `prompt` references) runs an agent in a **native harness** (Codex, Claude Code, OpenCode) chosen only by profile `name`; you cannot supply an executable, arguments or environment, and an unknown profile, over-broad `permissions`, or unsupported `require` capability is refused before dispatch.

- Input: `profile`, `prompt`, `output_schema` (required local JSON Schema), optional `instructions`, `inputs` (object), `permissions` (`read-only` default or `workspace-write`, never above the profile), `require` (capabilities).
- Output: `.result` (validated by `output_schema`), `.artifacts` (workspace file manifest with small text content), `.harness` (adapter, version, requested/served model, session ID, timings, usage), `.diagnostics`. Dependent steps reference e.g. `${/steps/work/output/result/answer}`.
- Inspect `effects[].harness_attempt` for the exact attempt state. A completed result is receipted and reused on replay; it is never run again. Timeout, cancellation, non-zero exit, malformed output or process loss (including a Forge crash: the surviving harness tree is terminated at restart, `orphan_terminated`) leaves `RECOVERY_REQUIRED`: no automatic retry or replacement session. Forge does not sandbox harnesses beyond their native permission modes, and runner listings show executable file names, argument counts and env names only. Tool actions the harness performed before failing may have happened; reconcile only with settled evidence (`runs reconcile --effect-id`).
- Existing actors need `harness` in their allowed types. See [the harness guide](../../docs/harness.md) for limits and runner verification.
